# Engineering Standards

Status: project operating standard
Audience: Efe, teammates, and AI coding agents

These rules define the default engineering taste for Atlas.
They apply to code, docs, PRs, reviews, tests, and implementation plans.

## Writing

- Never use the em dash character.
- Use a plain hyphen instead.
- When writing commit messages, never add an agent name as co-author.
- Do not manually edit `CHANGELOG.md` or files marked as generated, auto-generated, machine-generated, or generated by a command.
- If a generated file must change, run or document the generator.
- When writing or substantially editing long Markdown files, put each full sentence on its own physical line.
- Preserve normal Markdown structure.
- Avoid wrapping multiple full sentences onto one physical line.
- Use English for repo docs, code comments, issue templates, PR templates, and public technical artifacts unless explicitly told otherwise.

## Technical Decisions

- Do not give much weight to development cost when choosing architecture.
- Prefer quality, simplicity, robustness, scalability, security, and long-term maintainability.
- If a direction is too expensive or too large, reduce feature scope instead of weakening architectural correctness.
- Do not choose a dependency only because it is fashionable or fast.
- Do not avoid a necessary dependency only because it adds setup work.
- Use current official docs and real repo evidence before integrating external packages, providers, or services.

## Bug Fixes

- Start bug fixes by reproducing the bug as close to the end-user experience as practical.
- Prefer E2E reproduction for user-visible bugs.
- If full E2E reproduction is not practical, document the closest reproduction and why.
- Fix the root cause, not only the symptom.
- Add a regression test at the lowest level that proves the behavior.
- Keep the fix scoped, but do not silently ignore adjacent breakage found during investigation.
- If adjacent breakage is small and safe, fix it in the same PR.
- If adjacent breakage is larger or risky, create a tracked issue and call it out in the PR.

## UI Quality

- Be picky about UI during E2E testing.
- Use `agent-browser` screenshots and snapshots for implemented UI and preview verification.
- Check desktop and mobile when the surface is user-visible.
- Treat overlap, broken spacing, unreadable contrast, clipping, layout shift, and awkward empty/error states as real defects.
- If something clearly looks off and is small to fix, fix it.
- If it is outside scope, create a tracked issue and do not pretend the UI is polished.

## Test And CI Discipline

- Treat lint failures, type errors, test failures, and flaky tests as engineering defects.
- Do not ignore failures because they appear unrelated.
- If a failure is caused by the current change, fix it before completion.
- If a failure is pre-existing and small to fix safely, fix it.
- If a failure is pre-existing and larger than the current scope, document it with evidence and create a follow-up issue.
- Do not claim work is complete while relevant verification is skipped without a reason.

## Secrets And Generated Artifacts

- Never put secrets in docs, screenshots, fixtures, logs, generated artifacts, PR bodies, or issue comments.
- Production runtime secrets must not be used for ordinary local development.
- Shared dev secrets must stay scoped to dev/integration use.
- Generated artifacts should be reproducible from documented commands.
